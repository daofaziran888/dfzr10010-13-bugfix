# 湖仓一体化治理平台

面向数据架构师的湖仓一体化治理平台。覆盖数据湖表格式管理、Iceberg/Hudi表优化、小文件合并、数据压缩策略、元数据服务、表快照管理、数据分支合并与数据回滚恢复的完整湖仓治理链路。

这是一个前后端分离的管理平台：前端 Vue 3 + Vite + TypeScript，后端 FastAPI（Python）。
两边各自独立启动，前端 dev server 已关掉自动打开页面，启动后按终端打印的地址手工打开。

## 目录结构

```text
.
├── frontend/                 Vue 3 + Vite + TypeScript 前端
│   ├── src/views/            每个业务模块一个页面
│   ├── src/api/              统一请求封装
│   ├── src/stores/           会话与筛选状态
│   └── vite.config.ts        dev server 配置（open: false）
├── backend/                  FastAPI（Python） 后端
│   ├── app/routers/          每个业务模块一组接口
│   ├── app/services/         业务规则与状态流转
│   └── app/store.py          内存数据仓库与示例数据
├── .gitignore
└── docker-compose.yml
```

## 启动

### 后端

```bash
cd backend
python3 -m venv .venv && .venv/bin/pip install -r requirements.txt
./run.sh
```

健康检查：`curl http://127.0.0.1:8000/api/health`

### 前端

```bash
cd frontend
npm install
npm run dev
```

前端默认监听 `http://127.0.0.1:5173/`，dev server 不会自动打开浏览器，
需要自己访问。`/api` 由 vite 代理到后端 `http://127.0.0.1:8000`。

## 约定

- 每个模块的前端页面在 `frontend/src/views/<模块>/index.vue`，后端接口在
  `backend/app/routers/<模块>.py`，业务规则在 `backend/app/services/<模块>.py`。
- 列表接口统一返回 `{ items, total, page, size }`，动作接口统一返回 `{ ok, message }`。
- 状态流转只允许在 `app/services` 里改，路由层不做业务判断。
- 动作接口同时接受 `{"values": {"action": ...}}` 与扁平的 `{"action": ...}` 两种请求体。

## 数据过期清理取数链路

清理策略状态机为「草稿 → 已启用 → 执行中（执行期间短暂占用，落账后回到已启用）→ 已关闭」：

- `立即执行` / `继续清理` 只对已启用策略开放；执行结束一定回到「已启用」，不残留执行中；
  `关闭清理` 后策略为「已关闭」且不再接受执行动作，历史结果清单与审计清单保留。
- 过期条件按 `分区字段 比较符 日期`（如 `dt < 2026-08-01`）解析，结合分区目录
  （`app/seed.py` 的 `PARTITION_CATALOG`）确定清理范围。
- 每次执行生成一个批次，**清理行数只按该批次累计**；`继续清理` 沿用同批次号，只补
  结果清单里未完成（失败/中断）的分段，已删除、已跳过的确认结果不覆盖。
- 被有效回滚单（数据回滚恢复模块中待回滚/回滚中/已回滚）覆盖的分区禁止删除：
  - 清理方式「跳过冲突分区」：只跳过被引用快照覆盖的分区，其余分区照常清理；
  - 清理方式「整表暂停」：先全量预判冲突，命中则本轮整张表一个分区都不删除。
- 失败、异常、空态、无数据分区都在结果清单保留说明并可重试，不产生删除行数。

两份清单（内存表 `cleanup_results` / `cleanup_audits`）：

- `GET /api/cleanup/results` 清理结果清单：逐分区记录结果状态、实际删除行数、跳过原因、
  回滚记录编号与快照编号，被恢复链保护的分区按实际删除行数（0）保留。
- `GET /api/cleanup/audits` 清理审计清单：批次恢复结论、跳过分区、恢复引用、失败/空态分区。
- 快照模块消费同一份结果清单：先调 `GET /api/snapshot/{id}/cleanup/compatibility`
  做兼容性校验，再通过 `POST /api/snapshot/{id}/cleanup/consume` 消费，并把版本依据
  （快照编号/快照版本）回写到对应批次的清理审计清单；可恢复依据见
  `GET /api/snapshot/cleanup/recoverable-refs`。清理列表页与快照详情页读取的是同一份
  结果清单，两入口数据一致。
